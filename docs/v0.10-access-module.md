# v0.10 — UniFi Access module

Scope doc for the third module (after Network, Protect). Decisions locked 2026-05-27.

## Decisions

| Decision | Locked |
|---|---|
| Auth model | **Option A**: API-key reads only. No username/password session storage. No write tools in v0.10. |
| Dev environment | **Stub mode only**. Real-mode client written but not exercised against hardware in v0.10. Community tester or future hardware acquisition validates real mode in v0.10.x. |
| Release shape | **Single v0.10 release** with all read-only tools at once. No v0.10 + v0.11 split. |

## Goal

Add a UniFi Access surface so the project covers all three major UniFi applications. Eliminates the "doesn't do doors/credentials" objection vs sirkirby's product, while preserving the API-key-first security posture established in v0.9.x.

Target: **18 read-only tools**, putting the project at **86 total** (57 Network + 11 Protect + 18 Access).

## Architecture (mirrors Protect module)

```
src/mcp_unifi/
  clients/
    access.py              # AccessClient (httpx wrapper, /proxy/access/api/v2/)
    access_stubs.py        # AccessStubState (in-memory state machine)
  backends.py              # add AccessBackend, AccessRealBackend, AccessStubBackend
  dispatcher.py            # register "access" module on MCP_UNIFI_MODULES_ENABLED=...,access
  modules/
    access/
      __init__.py          # register() wires the 28 tools
```

Opt-in via `MCP_UNIFI_MODULES_ENABLED=network,protect,access`. Default stays `network` only.

## Auth model

**Option A locked**: API-key reads only.

UniFi Access has a wrinkle: mutations require a local username/password session (`/api/auth/login` → `/proxy/access/api/v2/...`), not the local API key. The API key only works for read-only queries on port 12445.

By choosing Option A we keep the v0.9.x API-key-first posture intact. No admin password ever sits in env. The 18 read-only tools cover forensics, audits, summaries, and visibility — the bulk of LLM use cases for Access.

Write operations (door unlock, credential issue, visitor pass create, device reboot, policy update) are **deferred to a future v0.11+** and gated by:
- Actual user demand, and
- A separate explicit decision to introduce session-token auth alongside the API key.

If that decision ever comes, the shape is: `UNIFI_ACCESS_USERNAME` + `UNIFI_ACCESS_PASSWORD` added to `Settings` (wrapped in `SecretStr`), separate session-aware client path, all writes flow through it. The bearer-token auth from v0.9.x still gates the MCP transport unchanged.

## Tool surface (18 read-only tools)

### Doors (3)
- `list_doors` — all doors with hub assignment, locked state, last activity
- `get_door` — one door, full state
- `list_door_groups` — group definitions

### Access policies (2)
- `list_access_policies` — schedules + which credentials apply where
- `get_access_policy` — full policy detail

### Credentials (3)
- `list_credentials` — all NFC cards / PINs / mobile credentials, with expiry
- `get_credential`
- `audit_expiring_credentials` — surfaces credentials expiring in N days

### Visitors (2)
- `list_visitors` — active and past visitor passes
- `get_visitor`

### Events (4)
- `list_access_events` — historical badge scans, door opens, denials with filters
- `get_recent_access_events` — last N events for quick triage
- `summarize_access_activity` — aggregated by door/user/policy over a window
- `list_failed_access_attempts` — denied entries (useful for security audits)

### Devices (2)
- `list_access_devices` — hubs, readers, relays, intercoms
- `get_access_device` — one device, health/firmware

### System (2)
- `get_access_system_info` — controller version, license, capacity
- `list_access_users` — people enrolled in the system

### Composites
- None in v0.10. Composites that combine reads (e.g. "show me everyone who badged into the server room after-hours this week") are expressible as multi-tool sequences the LLM composes itself; a dedicated composite isn't worth the complexity. Real composites land when write tools land.

## Out of scope for v0.10

- **All write operations**: door unlock/lock, credential create/revoke, visitor pass create/delete, policy update, device reboot. Gated by a separate Option B decision.
- Real-time event streaming via WebSocket (sirkirby has this; defer to v0.11+)
- Intercom call handling
- Camera-feed correlation across Access + Protect (interesting but multi-module, defer)
- Mobile credential push enrollment flows
- Hardware-validated real-mode integration test (Pete has no Access hardware; stub-mode dev + respx-mocked real-mode tests are the v0.10 substrate)

## Stub state

`AccessStubState` seeds:
- 2 doors ("Main Entrance", "Server Room"), 1 door group
- 1 access policy (business hours, all users)
- 3 credentials (1 NFC, 1 PIN, 1 mobile)
- 1 active visitor pass
- 50 synthetic events (mix of grants and denials over the last 24h)
- 1 hub, 2 readers

Same pattern as `ProtectStubState`. All mutating tools update stub state so the agent's experience is identical to real mode.

## Out-of-scope: positioning

This is not a "match feature count" exercise. The Access module makes the project credible as a complete UniFi MCP, not as the most feature-rich. Pete's positioning stays:

> Fewer tools than sirkirby. Each one engineered for LLM tool selection (`dry_run`, audit, rollback). Bearer-token-authenticated. Cosign-signed. SBOM-attested. Helm chart for k8s.

The Access module reinforces that — same dry-run, same audit, same composite rollback pattern. No regression in product posture.
